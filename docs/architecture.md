# Архитектура CampusFlow — пилота ИИМРТ

## Допущения

- Первая версия использует снимок 188 групп ИИМРТ за первое полугодие 2026/27. Доступность показывается только в пределах явно указанного покрытия. Пары других институтов могут занимать те же аудитории.
- Часовой пояс кампуса — Asia/Yekaterinburg. В БД интервалы хранятся как timestamptz. Даты, сетка звонков и границы учебного дня определяются по местному времени.
- Численность групп, вместимость, тип аудитории и оборудование подтверждает администратор. Лабораторные и число групп в одном слоте сохраняются как наблюдения с источником. Пустые характеристики означают «неизвестно».
- Допустимые переносы остаются предложениями до решения диспетчера. В пилоте эту функцию выполняет администратор. Утверждённое изменение применяется к копии расписания CampusFlow.
- Сначала проверяем книжку броней и оптимизатор на исторических данных. Дату демо можно выбрать вручную. Действующее бронирование на текущую дату требует актуальной загрузки расписания.

## Архитектура

React + TypeScript + Vite → FastAPI на том же origin → PostgreSQL через SQLAlchemy 2 и миграции Alembic. Python 3.11+. Docker Compose поднимает PostgreSQL, выполняет миграции, запускает API, фоновый обработчик и веб-сервер со сборкой Vite. Веб-сервер проксирует /api на FastAPI.

Модули API: auth, schedule, rooms, bookings, analytics, admin. Прикладные сервисы: поиск и проверка интервалов, разбор и публикация импорта, оптимизация, модель ранжирования. Короткие операции выполняет API, длительные задания импорта и оптимизации обрабатывает отдельный процесс через таблицу заданий. Задание получает идентификатор, статус, отметку прогресса и результат или ошибку. Повтор обработки безопасен благодаря идентификатору задания и проверке состояния перед публикацией.

Из прототипа переносим правила ролей, проверку интервалов, разбор JSON и расчёт окон. Используем исходный schedule.json и сохраняем исходные обозначения ИСУ для сверки. Новый сервер разворачивается на отдельной PostgreSQL БД. Перенос локальных броней SQLite в этот этап не входит.

JWT доступа с коротким сроком хранится в памяти клиента и передаётся в Authorization. Обновление по ротационному токену в HttpOnly/SameSite cookie. База хранит хеши токенов обновления. Проверки роли, статуса аккаунта и владельца брони выполняются сервером. Для университетского SSO предусмотрены идентификатор провайдера и внешний subject. Персональные данные отделены от публичного представления занятости.

## Схема БД

| Таблица | Основные поля и связи |
|---|---|
| users, auth_identities, refresh_sessions | Аккаунт, роль student/teacher/admin, статус. Локальный логин и хеш пароля либо уникальная пара provider/subject. Сессия связана с пользователем. |
| buildings, rooms, equipment, room_equipment | Уникальный номер аудитории в пределах корпуса. Тип, вместимость, флаг активности. Оборудование и количество. |
| room_evidence | Аудитория, версия импорта, доля лабораторных, максимум одновременно наблюдавшихся групп. |
| groups, teachers, favorites | Группы с численностью, преподаватели с внешними идентификаторами и необязательной связью с аккаунтом. Одна избранная группа на пользователя. |
| bell_slots | Номер пары, локальные начало и конец, срок действия сетки. |
| import_batches, import_issues | Контрольная сумма, источник, состояние, отчёт, даты покрытия. Ошибки разбора и сопоставления. |
| terms, schedule_versions | Границы семестра, активная версия для области покрытия, ссылка на импорт. |
| lessons, lesson_groups, lesson_teachers | Конкретное занятие с дисциплиной, видом, требованиями, стабильным ключом источника и интервалом. Связи многие-ко-многим для потоков и преподавателей. |
| bookings | Владелец, причина брони, отменивший пользователь и время отмены. |
| room_occupancy | Аудитория, interval tstzrange, вид lesson/booking/block, ссылка на занятие или бронь. Содержит только активную занятость. |
| teacher_preferences | Преподаватель, интервал или день недели, жёсткая недоступность либо пожелание. |
| jobs, optimization_proposals, audit_log | Статус задания, версия расписания, предлагаемые изменения, оценка до/после, история административных действий. |

Занятия, брони и блокировки используют одну таблицу занятости. Полуоткрытые интервалы [начало, конец) разрешают два смежных слота. Ограничение GiST EXCLUDE по room_id WITH = и interval WITH && с btree_gist служит последней проверкой при параллельных запросах. Вставка брони и её интервала, отмена и освобождение интервала выполняются в одной транзакции. Нарушение ограничения возвращает 409. При публикации импорта сервер атомарно заменяет интервалы занятий и сохраняет существующие брони. Конфликты с бронями блокируют публикацию и отображаются в отчёте. Данные с неразрешимым наложением внутри источника остаются в предварительном просмотре до проверки.

При импорте сохраняем все занятия и объединяем подтверждённые записи одной пары, пришедшие из расписаний нескольких групп. Равенство времени и аудитории само по себе не доказывает, что две записи — одно занятие. Неизвестные аудитории и неполные периоды отражаются в покрытии запроса.

## API

Префикс /api/v1. Для ошибок возвращаем стабильный код и текст на русском. Поиск, таймлайн и аналитика включают информацию о покрытии. Списки аудиторий, броней и пользователей поддерживают постраничную выдачу.

| Метод и путь | Доступ и результат |
|---|---|
| POST /auth/login, /auth/refresh, /auth/logout; GET /auth/me | Вход, обновление и завершение сессии, профиль и роль |
| GET /groups; PUT /me/favorite-group | Все роли. Поиск групп и сохранение избранной |
| GET /schedule?group_id&from&to | Все роли. Занятия группы |
| GET /rooms; GET /rooms/occupancy?date&building_id&type&min_capacity | Все роли. Каталог и интервалы занятости с фильтрами без сведений о владельцах броней |
| GET /slots?start&duration&building_id&type&min_capacity | Все роли. Подходящие интервалы и ближайшие варианты. Свободный интервал за пределами покрытия не подтверждается |
| POST /bookings; GET /bookings/mine; POST /bookings/{id}/cancel | Преподаватель и администратор. Создание и список своих броней, отмена своей или любой для администратора |
| GET /analytics/windows?from&to | Преподаватель и администратор. Окна групп и преподавателей с указанием покрытия |

| GET /admin/bookings; POST /admin/rooms; PATCH /admin/rooms/{id} | Администратор. Все брони, характеристики аудиторий |
| POST /admin/imports; GET /admin/imports/{id}; POST /admin/imports/{id}/publish | Администратор. Валидация снимка, отчёт, атомарная публикация |
| GET /admin/users; POST /admin/users; PATCH /admin/users/{id} | Администратор. Создание аккаунтов, статус и роль |
| POST /admin/optimization-runs; GET /admin/optimization-runs/{id}; POST /admin/optimization-runs/{id}/apply | Администратор. Запуск, варианты с метриками и применение после повторной проверки версии и конфликтов |

## Этапы и критерии готовности

1. Архитектура, схема и контракт API — этот документ.
2. PostgreSQL, Alembic, JWT и бронирование. База принимает ровно одну из двух параллельных броней одного слота. Проверяем смежные слоты, конфликт с занятием, права всех ролей и отмену.
3. Импорт ИСУ. Прогон на 188 группах, сверка охвата, повторный импорт без дубликатов, отчёт об ошибках и предварительный просмотр перед публикацией.
4. OR-Tools CP-SAT строит допустимые переносы по сетке звонков. Жёсткие условия: непересечение по группам, преподавателям и аудиториям, недоступность, вместимость, оборудование, действующие брони. Цели: меньше окон и переносов, соблюдение пожеланий по дням без пар. Scikit-learn ранжирует допустимые предложения при наличии истории решений. Сравниваем на отложенных периодах с простым ранжированием по выигрышу в окнах. До появления данных используем это простое ранжирование.
5. React-интерфейс. Главный экран — «Занятость аудиторий»: строки аудиторий и сетка времени, занятые интервалы со штриховкой и текстом. На телефоне тот же день доступен списком интервалов. Кнопка «Свободно сейчас» подставляет текущее время кампуса, второй клик открывает подробности аудитории. Отдельные экраны: «Расписание» с избранной группой, «Бронирование» с шагами параметры → варианты → подтверждение и вкладкой «Мои брони», «Аналитика», «Админка» с аудиториями, импортом и пользователями. Спокойная палитра с одним акцентом, локальные кириллические шрифты, светлая и тёмная темы. Проверяем WCAG 2.2 AA: контраст, видимый фокус, клавиатуру, текстовые статусы, сообщения загрузки и ошибок.
6. Docker Compose, pytest для оптимизатора, конфликтов и ролей, проверка запуска на пустой базе. README включает развёртывание, настройку секретов, резервное копирование и раздел про обработку данных по 152-ФЗ с проверкой актуальных требований перед публикацией.

## Уточнения по полному брифу

### Охват и права

- Каталог пилота ограничен корпусами 6 и 7 на ул. Карла Маркса. Расписание групп сохраняем и для занятий вне этих корпусов, чтобы видеть окна и пересечения. Дополнительные выгрузки корпусов нужны целиком, включая занятия других институтов. До их загрузки пустой интервал показываем как «нет данных о занятости».
- В доступных файлах есть JSON 188 групп. Отдельных выгрузок корпусов и истории посещения броней пока нет. Для импорта принимаем XLSX/CSV с сопоставлением столбцов и ICS с раскрытием повторов и исключений в пределах семестра. Для ICS связь с аудиторией, группой и преподавателем проверяется при предпросмотре. Неразрешённые поля попадают в отчёт.
- Расписание открывается по группе, преподавателю, аудитории и корпусу. Поиск преподавателя для студента использует обезличенные обозначения. Начальный каталог фильтруется по этажу, типу, подтверждённой вместимости, оборудованию и доступности для маломобильных. При прочих равных предпочтение получает аудитория с меньшим запасом мест.
- Роль admin объединяет диспетчера и администратора в пилоте. На публичных и студенческих экранах скрываем ФИО. Инициалы, если необходимы, доступны после входа. Журнал административных действий хранит псевдонимизированный ID, время и тип операции.

### Жизненный цикл удержания и импорта

1. Создание hold фиксирует срок 5 минут по часам PostgreSQL. В одной транзакции блокируем строку аудитории, освобождаем её просроченные удержания и пробуем вставить интервал. EXCLUDE остаётся проверкой пересечений. Фоновая уборка освобождает просроченные интервалы. Поиск считает активными удержания со сроком позже текущего времени БД.
2. Подтверждение блокирует удержание в том же порядке, проверяет владельца и срок, создаёт бронь и переводит существующий интервал из hold в booking в той же транзакции. Так у конкурирующего запроса нет промежутка, в котором слот свободен. Клиент получает абсолютное время истечения и показывает таймер. Результат 409 содержит код причины и до трёх ближайших вариантов в рамках покрытия.
3. Импорт хранится как версия с контрольной суммой и областью покрытия. После сопоставления колонок и проверки предпросмотр показывает ошибки, неизвестные аудитории и пересечения. Откат активирует предыдущую версию после повторной проверки действующих броней и удержаний. Публикация и откат меняют интервалы в одной транзакции. Реальные файлы и артефакты на их основе храним вне Git, для тестов и демо в репозитории используем синтетический набор.
4. Интеграционный тест запускает 100 независимых параллельных попыток с разными идемпотентными ключами на одном слоте в PostgreSQL. Ожидаемый результат — одно удержание, 99 ответов 409, одна итоговая бронь после подтверждения победителя. Отдельно проверяем 100 прямых параллельных попыток записи занятости на уровне БД, повтор ключа, истечение удержания и конфликт с парой.

### Оптимизатор, прогноз и данные

CP-SAT назначает слоты и аудитории. Варианты с нарушением требований к типу, вместимости, оснащению, доступности, занятости и обязательной недоступности преподавателя исключаются. Сравниваем исходное расписание и вариант по окнам групп и преподавателей, переходам между корпусами, лишним местам, разбросу загрузки и количеству переносов. Переезд между корпусами внутри слишком короткой перемены запрещаем по настраиваемому нормативу. При поиске топ-3 берём факторы из расписания и каталога и формируем объяснения шаблонами по проверяемым данным.

Scikit-learn обучает две отдельные модели. Загрузку по корпусу, типу, дню и часу прогнозируем по исторической занятости известных интервалов и проверяем на более поздних неделях с метриками и сравнением с историческим средним. Факт занятия по расписанию не даёт факта явки на бронь. Для модели неявки до появления отметок посещения используем только синтетические события с явной маркировкой в UI и README. Синтетическую оценку не применяем для автоматической отмены или отказа.

Все ресурсы и обработка локальные. Перед развёртыванием университет определяет основание обработки, сроки хранения, правила удаления, текст политики и ответственных за доступ. На этапе 6 документируем эти параметры и сверяем текст с актуальными требованиями.

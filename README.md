# CampusFlow

Расписание, занятость и бронирование аудиторий корпусов 6 и 7 ИИМРТ.

## Локальный запуск

На Windows откройте Docker Desktop и запустите `run_dev.cmd` двойным щелчком.
Тот же файл запускает сайт после правок и пересобирает изменённые образы.
Данные остаются в томе PostgreSQL. По умолчанию скрипт использует порт 8768.

Из PowerShell в папке проекта:

```sh
.\run_dev.cmd
```

Откройте http://127.0.0.1:8768/. Сценарий показа и учётные записи приведены
в [описании демостенда](docs/demo.md). API доступен по префиксу `/api/v1`.


## Что показать жюри

1. На главной откройте «Роли, логины и пароли». Студент может показать свободные аудитории и расписание группы АСУ-31.
2. Нажмите «Сменить роль» и войдите преподавателем. Укажите число участников, выберите оборудование и нажмите «Подобрать». Выберите аудиторию, удержите интервал и подтвердите бронь.
3. Переключитесь на сотрудника деканата, откройте группу в рейтинге и сравните предлагаемые переносы.
4. Войдите администратором, чтобы показать управление пользователями, аудиториями и импортом.

Для сдачи подготовьте четыре URL: репозиторий, доступный извне веб-стенд, README
в репозитории и презентацию. Проверьте открытие ссылок в приватном окне.
Локальный адрес подходит для репетиции. Для показа используйте синтетический стенд.
О настройке Qwen и границах анализа читайте в [описании модели](docs/ranking.md).

## Развёртывание в университете

1. Используйте отдельное имя проекта Compose и новый том PostgreSQL для университетской
   установки. Скопируйте `.env.example` в `.env`. Задайте разные случайные URL-безопасные
   секреты для PostgreSQL, JWT и псевдонимизации (минимум 32 байта для каждого).
   Ограничьте доступ к файлу. Основной compose.yaml отключает демонстрационный режим и требует HTTPS для сессии. Режим демо рассчитан на локальный синтетический стенд.
2. Разместите проект на узле университета. Запустите
   `docker compose -p campusflow-university up --build -d`.
   Только веб-интерфейс слушает адрес loopback. PostgreSQL и API доступны внутри
   сети Compose. Университетский HTTPS-прокси направляет запросы на
   `127.0.0.1:8767`, передаёт исходный Host и выставляет
   `X-Forwarded-Proto: https`. Пользовательский заголовок с таким именем
   прокси должен перезаписать. Проверяйте журналы через
   `docker compose -p campusflow-university logs api web`.
3. Создайте первую учётную запись администратора через
   `docker compose -p campusflow-university exec api python -m app.v1.cli user dispatcher admin`.
   Пароль вводится интерактивно. Добавьте подтверждённые сведения об аудиториях
   и импортируйте расписания ИИМРТ и обоих корпусов через админку. Доступность
   подтверждается на период опубликованного полного расписания корпуса.
4. Перед обновлением сделайте резервную копию PostgreSQL в защищённом хранилище
   университета. Например на сервере Linux:
   `docker compose -p campusflow-university exec -T db pg_dump -U campusflow -Fc campusflow > campusflow.dump`.
   Проверяйте восстановление `pg_restore` в отдельную базу. Ключ псевдонимизации
   требуется сохранять при обновлениях и защищать отдельно от копии базы.

## Персональные данные и 152-ФЗ

Пилот хранит локальные логины, роли, хеши паролей, псевдонимы преподавателей,
записи о бронировании, версии опубликованного расписания и журнал административных
действий. При разборе расписания ФИО из поля преподавателя заменяется псевдонимом,
а исходный файл после разбора удаляется из временного хранилища загрузки.
Поле названия брони и свободный текст расписания могут содержать введённые человеком
сведения. Перед импортом проверяйте эти поля. Псевдонимизированные записи
обрабатывайте как потенциально персональные данные. Реальные выгрузки, дампы,
секреты и модели, обученные на университетских данных, храните вне Git.

До работы с реальными данными университет определяет цели и основания обработки
(ст. 5–6), утверждает политику и организационные меры (ст. 18.1), применяет меры
защиты (ст. 19) и утверждает порядок уточнения, блокирования и удаления (ст. 21).
Определите сроки отдельно для броней, версий импорта, журналов и резервных копий,
включая проверяемую процедуру удаления. Пилот автоматически удаляет истёкшие
удержания из активной занятости при следующем бронировании. Очистка и удаление данных аккаунта описаны в [регламенте пилота](docs/privacy.md). Перед подключением реальных пользователей замените черновой текст
политики, определите форму согласия и оцените необходимость уведомления
Роскомнадзора применительно к вашему процессу. CampusFlow запоминает приём каждой редакции. Отзыв из личного кабинета завершает все сеансы.
Тексты документов — шаблоны для согласования с юристом и ответственным за обработку данных. Реквизиты и версия описаны в [регламенте пилота](docs/privacy.md).

Шрифты и ресурсы поставляются локально. Во время работы приложение не использует
внешние сервисы аналитики или CDN. Разбор окон использует локальную Ollama. Для сборки Compose нужны образы и пакеты,
которые можно доставить через внутренний реестр университета.

[Текст 152-ФЗ](https://mintrud.gov.ru/docs/laws/130)

## Возможности CampusFlow

- Расписание использует недельную сетку по звонкам из конфигурации сервиса. Доступны ссылки на выбранную группу, режим дня, печать и экспорт в PDF и Word. Для студентов поиск аудитории на время окна доступен после выбора своей группы в профиле.
- Аудитории на выбранное время показываются только при подтверждённом импорте. Диспетчер выдаёт код отметки и размещает его у двери. Этот способ проверяет знание кода. Для подтверждения физического присутствия вузу понадобится сканер или СКУД.
- Повторяющаяся бронь создаётся одной транзакцией. При конфликте любой даты серия не публикуется. Список ожидания и напоминания работают внутри сайта.
- Аккаунт хранит группу, корпус, тему, плотность и настройки уведомлений. Восстановление пароля — одноразовая ссылка диспетчера сроком на 30 минут. SMTP не требуется.
- Учебные примеры и размеры демонстрационных групп синтетические. Реальные планы этажей, замеры переходов, расписание и реквизиты оператора добавляет вуз.
- [Модель переносов и ограничения](docs/ranking.md).

Если Docker прерывает сборку на образе node:22-alpine, запустите `.
un_dev.cmd --pull-base`.
При временной недоступности Docker Hub команда `.
un_dev.cmd --no-build` запускает
предыдущую локальную сборку, если она есть. Для применения новых изменений нужна обычная пересборка.

## Бронирование и рейтинг групп

Основной сценарий CampusFlow — самостоятельное бронирование аудиторий. В compose используется CAMPUSFLOW_BOOKING_MODE=standalone. Каталог и брони работают без выгрузки расписания. Любые опубликованные занятия, брони и активные удержания продолжают занимать аудитории в общем реестре. Для подключения университета можно выбрать режим schedule, в котором требуется полная выгрузка корпуса.

Студент смотрит свободные аудитории и расписание. Преподаватель начинает с бронирования и может открыть своё расписание. Деканат сравнивает расписания групп и применяет проверенные переносы. Администратор управляет пользователями, аудиториями, импортом и бронями.

Для демонстрации используйте корпус «Практикум» с 16 аудиториями и 16 синтетическими группами. Пошаговый сценарий передачи освободившейся аудитории между двумя пользователями описан в [инструкции для демонстрации](docs/demo.md).


Качество расписания оценивается от 0 до 100. Штраф равен округлённой сумме минут окон / 12, самого длинного окна / 12, числа окон × 2 и смен корпуса × 4. Качество равно 100 минус штраф, ограниченный 100. Это стартовые веса прототипа, которые требуют согласования с деканатом. Количество занятий и дней без окон показывается рядом с оценкой. Окна считаются внутри учебного дня по сетке звонков.

Локальная Qwen через Ollama получает только числовую сводку и выбирает пояснения. Баллы вычисляет сервер. OR-Tools предлагает перемещение существующего занятия, сохраняя дисциплину, группы и преподавателей. Сотрудник принимает предложение после сравнения. После обновления занятости или ограничений применимость проверяется повторно.

Преподаватель выбирает дни без занятий в личном кабинете. Они действуют для новых предложений после привязки аккаунта к псевдониму. Существующие занятия не переносятся автоматически. Предложение отклоняется, если увеличивает суммарные внутридневные перерывы хотя бы одного затронутого преподавателя. Проверка выполняется при подборе и при принятии, включая частичное принятие.
